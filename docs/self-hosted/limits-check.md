# Limits check: spec 001 vs today's servers and clients

Sources. New limits: `docs/specs/001_backend_api.md` §5-§11 (API-031, 050, 070, 071, 080, 092, 093, 101, 110, 120, 130, 140-147) and `docs/self-hosted/backend.proto` comments. Today's servers: `docs/self-hosted/existing/xmtp-node-go.md` (v3), `docs/self-hosted/existing/xmtpd.md` (v4), `docs/self-hosted/existing/xip-83.md`. Today's clients: `docs/self-hosted/existing/libxmtp-api-callers.md` (§5, §8, R1-R46) and the client code cited per row.

Verdicts. SAFE: the new limit is at or above what the client sends. TIGHTER: below a server limit that exists today, but the client never reaches it (margin given). BREAKS: a request that works today against v3 or v4 is rejected, or returns silently truncated data, under the new limits.

## BREAKS

1. **Publish, 50 envelopes (row 5).** On a proposals-enabled group, one membership update publishes one Add proposal per new installation plus one Remove proposal per removed leaf plus one extension proposal plus the commit, all in one `send_group_messages` call (`crates/xmtp_mls/src/groups/mls_sync/update_group_membership.rs:282-301,402-440`; `mls_sync.rs:3189-3196`). Adding 5 inboxes with 10 installations each already exceeds 50. v3 and v4 accept this today (no count cap; 50 MiB and 25 MiB). Chunking at 50 also loses API-030 atomicity for one MLS commit and forces ordered, sequential chunks. Not listed in API-146.
2. **Query `limit` of 100 total across topics (row 2).** Identity-update reads send 50 inboxes per request with no limit; v4 returns up to 1000 rows and v3 returns the full tail. The new backend returns 100 rows plus `has_more`, and the client has no paging loop, so the association-state fold runs on a truncated log. Silent truncation, not a rejection. Commit-log reads degrade from 20 x 100 to 100 per tick. Not listed in API-146.
3. **Static subscription, 1000 topics (row 11).** The legacy stream, which is the default on every platform and the only path in browsers, sends every group in one `SubscribeGroupMessages` / `SubscribeTopics` request. v3 has no cap; v4 allows 10,000. A client with more than 1000 conversations is rejected. API-144 states the client rule, API-146 does not list it as new work.
4. **Newest-envelope with full envelopes, 100 topics (row 4).** Key-package fetch is unchunked and reaches 2500 keys. Acknowledged in API-140 and API-146.
5. **Inbox-id lookup, 250 identifiers (row 12).** `can_message` and `add_members_by_identity` are unchunked; 251 to 1000 works on both backends today. Acknowledged in API-141 and API-146.

## TIGHTER, worth confirming

- **Topics per bidi stream, 100,000 (row 9).** v3 has no cap, v4 allows 1,000,000. The client's one-wire-per-process design means an agent host that multiplexes many identities can reach it. The review log marks this value as awaiting confirmation.
- **Query topics per request, 1000 (row 1).** v4 allows 10,000; the client sends at most 50. No action needed.

## MISSING from the new spec (a limit that exists today, or that a client could exceed with no bound)

1. **Inbox log size.** v3 rejects the 257th identity update for an inbox (§10.1) and v4 validates against the newest 256 rows (§18). The spec sets no cap and API-043 implies validation over the full log. State either a cap or that validation reads the whole log.
2. **Per-envelope payload size.** v4 caps blockchain-bound envelopes (identity updates) at 200,000 bytes. The spec has only the 25 MiB request cap, so one 25 MiB group message or key package is accepted. Not a client break, but the only bound on a single row.
3. **SCW signatures per `VerifySmartContractWalletSignatures` request.** No limit stated; each signature is a chain RPC (API-044). The client sends 1 today but fans out with no cap (callers §5.12).
4. **Publish concurrency.** No server-side limit; API-142 places the cap on the client. Today's welcome fan-out opens up to ~2500 concurrent publishes (`mls_sync.rs:4636-4648`).
5. **Waves in flight per stream.** v4 caps at 256; API-093 leaves it unbounded. Looser, so no client break, but a server-protection gap.
6. **Rate limits, mutation rate, ping rate.** Deferred to Phase 6 (§14). The v3 `PUB` bucket (600/min, max 3000) is the figure a welcome fan-out of 2500 must still fit under.
7. **Query page `limit` accepted as a client value.** API-071 clamps larger values to 100; a test build sends `MAX_PAGE_SIZE` = 20 (`crates/xmtp_configuration/src/test/api.rs:4`), which is honored. No gap, noted for completeness.
