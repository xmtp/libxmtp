Robust group chat permissions are key to providing users with a friendly and safe group chat experience.

## Understand the group permissions system

### Member statuses

Member statuses are the roles that can be assigned to each participant (inbox ID) in a group chat. These are the available member statuses:

- Member
  - Everyone in a group chat is a member. A member can be granted admin or super admin status. If a member's admin or super admin status is removed, they are still a member of the group.
- Admin
- Super admin

When a group is created, all groups have the same initial member "roles" set:

- There is one super admin, and it is the group creator
- There are no admins
- Each user added to the group starts out as a member

## Permissions

A super admin can change the group's permission policies. Each action uses the policy assigned to it.

| Permission               | Allow all | Deny all | Admin only | Super admin only |
| ------------------------ | --------- | -------- | ---------- | ---------------- |
| Add member               | ✅        | ✅       | ✅         | ✅               |
| Remove member            | ✅        | ✅       | ✅         | ✅               |
| Add admin                | ❌        | ✅       | ✅         | ✅               |
| Remove admin             | ❌        | ✅       | ✅         | ✅               |
| Update group permissions | ❌        | ❌       | ❌         | ✅               |
| Update group metadata    | ✅        | ✅       | ✅         | ✅               |

## Permission policy sets

If you do not select a policy set, the group uses **All members**.

| Permission                                | All members | Admin only  |
| ----------------------------------------- | ----------- | ----------- |
| Add member                                | All members | Admin       |
| Remove member                             | Admin       | Admin       |
| Add or remove admin                       | Super admin | Super admin |
| Update permissions                        | Super admin | Super admin |
| Update name, description, image, app data | All members | Admin       |
| Update disappearing messages              | Admin       | Admin       |

DMs use neither set. Participants cannot change membership or permissions, and both can change metadata.

Add admin and remove admin cannot use an allow-all policy. A custom policy can allow admins to perform these actions. Only a super admin can update the permission policies or grant and revoke the super admin role.

### Custom policy set

A custom set contains nine policies: add member, remove member, add admin, remove admin, update name, update description, update image URL, update disappearing messages, and update app data.

Pass a custom `GroupPermissionMode` in `CreateGroupOptions.permissions`. The custom variant contains a `PermissionPolicySet`. This option is available on all four SDKs.

## Update permissions

All four SDKs use `group.updatePermission(kind, policy, metadataField)`. Use `PermissionUpdateKind` for the action and `PermissionPolicy` for the policy. For a metadata update, also pass `MetadataFieldKind`. This includes the disappearing-message and app-data policies. Swift uses the labels `kind:`, `policy:`, and `metadataField:`.

## Admins

| Action      | Method                                              |
| ----------- | --------------------------------------------------- |
| Check role  | `isAdmin(inboxId)`, `isSuperAdmin(inboxId)`         |
| List roles  | `listAdmins()`, `listSuperAdmins()`                 |
| Grant role  | `addAdmin(inboxId)`, `addSuperAdmin(inboxId)`       |
| Revoke role | `removeAdmin(inboxId)`, `removeSuperAdmin(inboxId)` |

These names are the same on all four SDKs. The calls are asynchronous. Swift uses `inboxId:` for the methods that take an inbox ID.

## Members

The backend sets the group member limit. The default limit is 250 inboxes.

Use `addMembers` and `removeMembers` with a list of inbox IDs or a list of `PublicIdentity` values. Swift uses the `members:` label. Call `members()` to read the member list on all four SDKs. These calls are asynchronous.

Sync before you read the member list.

## Leave a group

A member can request removal from a group by calling `requestRemoval()`. A super admin must process the request before the member is removed. After removal, the group becomes inactive for that member.

The call is refused if the caller is a super admin, is the only member, or is in a DM. After the request is processed locally, `group.state()` reports `membershipState` as pending removal. This does not mean that the member has already been removed.

## Group metadata

Group chats can have metadata, like names, descriptions, and images. Metadata can help users more easily identify their group chats.

| Field       | Update                           |       Limit |
| ----------- | -------------------------------- | ----------: |
| Name        | `updateName(name)`               |   100 bytes |
| Description | `updateDescription(description)` | 1,000 bytes |
| Image URL   | `updateImageUrl(url)`            | 2,048 bytes |
| App data    | `updateAppData(data, expected)`  | 8,192 bytes |

Read metadata from the asynchronous `group.state()` snapshot on all four SDKs. App data is a string. Pass the previous value as `expected` to update app data only if it still matches, or pass `undefined` on Browser and Node or `null`/`nil` on mobile to omit that check. Serialize structured data before you set it. See [Disappearing messages](/sdk/disappearing-messages/).
