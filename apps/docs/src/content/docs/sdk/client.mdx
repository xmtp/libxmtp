Create an XMTP client to connect an identity to your backend and keep its local messaging state.

## How it works

When you call `Client.create()` on Browser or Node, or `SDKClient.create()` on Kotlin or Swift, these steps occur:

1. The client asks the signer for its identifier.
2. It looks up the inbox ID registered for that identifier on your backend. If none exists, it derives an inbox ID from the identifier and a nonce.
3. It opens or creates the local database for that inbox and installation.
4. It asks the signer to register a new installation when needed, unless `registration.auto` is `false`.

### Keep the database encryption key safe

For Node, Kotlin, and Swift, generate a secure 32-byte encryption key and store it so the app can use the same key on every launch. If the key changes or is lost, the client cannot read the former encrypted database. Keep the same key when reopening it.

### The database is the installation

The database key and path select the stored installation. A different path can select a new database. In Swift, the wrong key fails to open an existing encrypted database with a typed storage error. It does not replace the stored key. A new installation needs a signature and counts against the backend's installation limit, which defaults to 10.

Store the key and path as durable app state. Keep the same storage location and label. An agent deployment must mount durable storage for `XMTP_DB_DIRECTORY`.

### Database encryption key loss during iOS device transfers

A restored or transferred database cannot open if the app does not also restore its encryption key. Choose a backup policy for the database and key together. If your app excludes the key from backups, you can also exclude the database directory from backups.

For example, if you set `StorageOptions.location` to a known directory, you can mark it as excluded from backups in iOS:

```swift
import Foundation

func addSkipBackupAttribute(folder: URL) throws {
  var folder = folder
  var values = URLResourceValues()
  values.isExcludedFromBackup = true
  try folder.setResourceValues(values)
}
```

To learn more about this function, see [isExcludedFromBackupKey](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey) in Apple's documentation.

### View an encrypted database

For debugging, it can be useful to decrypt a locally stored database. When `StorageOptions.encryptionKey` is used, the XMTP client creates a [SQLCipher database](https://www.zetetic.net/sqlcipher/) which applies transparent 256-bit AES encryption. A `.sqlcipher_salt` file is also generated alongside the database.

To open this database, you need to construct the password by prefixing `0x` (to indicate hexadecimal numbers), then appending the encryption key (64 hex characters, 32 bytes) and the salt (32 hex characters, 16 bytes). For example, if your encryption key is `A` and your salt is `B`, the resulting password would be `0xAB`.

The database also uses a [plaintext header size](https://www.zetetic.net/sqlcipher/sqlcipher-api/#cipher_plaintext_header_size) of 32 bytes.

If you want to inspect the database visually, you can use [DB Browser for SQLite](https://sqlitebrowser.org/), an open source tool that supports SQLite and SQLCipher. In its **Custom** encryption settings, set the **Plaintext Header Size** to **_32_**, and use the full **Password** as a **Raw key**:

![DB Browser for SQLite](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/db-browser-sqlite.png)

### Common database error

`PRAGMA key or salt has incorrect value` means the supplied encryption key does not match the database. It can also mean that the file is not an XMTP database. Do not replace the stored key automatically. A replacement key cannot open the existing encrypted database.

### Client options

For persistent Swift storage, pass a securely generated or caller-stored 32-byte
`databaseKey: Data`. Store it securely and reuse it when reopening the same
database. Omitting `encryptionKey` selects unencrypted storage. Pass the key for
all persistent locations: `StorageOptions(location: .default, encryptionKey:
databaseKey)`, `StorageOptions(location: .directory(directory: directory),
encryptionKey: databaseKey)`, or `StorageOptions(location: .explicit(dbPath:
dbPath, attachmentsDir: attachmentsDir), encryptionKey: databaseKey)`.

The SDKs share these client options. Browser and Node use JavaScript records.
Kotlin and Swift use `ClientOptions` and `StorageOptions` records.

| Option                     | Default           | Purpose                                                   |
| -------------------------- | ----------------- | --------------------------------------------------------- |
| `backend`                  | Supply explicitly | Connection options or a connected `Backend`               |
| `storage`                  | Supply explicitly | Database location, label, and native encryption key       |
| `deviceSync`               | `true`            | Enable device sync                                        |
| `allowOffline`             | `false`           | Start from stored state without backend requests          |
| `registration.auto`        | `true`            | Register the identity when needed                         |
| `registration.nonce`       | `0` when omitted  | Nonce for deriving an inbox ID when no association exists |
| `forkRecovery`             | Unset             | Fork recovery policy and group selection                  |
| `workers`                  | SDK defaults      | Background worker intervals                               |
| `handlers.preAuthenticate` | Unset             | Callback before a registration signature request          |
| `attachments`              | SDK defaults      | Attachment limits and private network access              |

Pass custom codecs in `ClientOptions.codecs` on Browser and Node. Kotlin and Swift
take a `codecs` argument on `SDKClient.create()` and `SDKClient.build()`.
Logging has a separate configuration API. See [Debug](/sdk/debug/#file-logging).

JavaScript storage locations are `"default"`, `"inMemory"`, `{ directory }`, or
`{ dbPath, attachmentsDir }`. Kotlin and Swift use the corresponding
`StorageLocation` variants. Browser storage uses OPFS and has no `encryptionKey`
option. Node, Kotlin, and Swift accept an optional 32-byte `storage.encryptionKey`.
Without that key, native storage is unencrypted.

A default or directory location stores each inbox under
`{root}/{deployment}/{inboxId}/xmtp.db3`. A non-empty `storage.label` adds one
directory below the root. An explicit location uses the supplied database and
attachments paths. Changing the location or label can select a new installation.

The default roots are `xmtp-sdk` in the Browser OPFS pool, `xmtp` in Node's current
working directory, `filesDir/xmtp_db` on Android, and
`Application Support/{bundleId}/xmtp` on Apple platforms. The Android default needs
an application context. The Apple default needs a bundle identifier.

JavaScript `backend` accepts `{ url, appVersion?, credentials? }` or a
connected `Backend`. JavaScript `credentials` accepts a `CredentialSource` or a
fixed `Credential`. Native `BackendOptions` has separate `credentials` and
`credential` fields. Create a reusable connection with `Backend.connect(options)`.
Kotlin uses `BackendSource.Options(options)` or `BackendSource.Connected(backend)`.
Swift uses `.options(options: options)` or `.connected(backend: backend)`.

### Backend authentication

If the backend requires an API key or JWT, supply a `CredentialSource` in
`BackendOptions.credentials`. Its async `credential()` method returns `value`,
`expiresAtSeconds`, and an optional header `name`. Browser and Node use a `bigint`
for expiry. Kotlin uses `Long`; Swift uses `Int64`. Expiry is in Unix seconds.
The default header name is `authorization`. For a bearer token, include `Bearer`
and one space before the token. This credential is separate from the XMTP signer
and the database encryption key.

The examples take an app function that obtains a token and its expiry. Fetch a
current token each time the callback runs. Do not log tokens or embed an
operator's secret in a public app.

```kotlin
fun authenticatedBackend(
    fetchToken: suspend () -> Pair<String, Long>,
): BackendOptions = BackendOptions(
    url = "https://xmtp.example.com",
    credentials = object : CredentialSource {
        override suspend fun credential(): Credential {
            val (token, expiresAtSeconds) = fetchToken()
            return Credential(name = null, value = "Bearer $token", expiresAtSeconds = expiresAtSeconds)
        }
    },
)
```

Pass these options through `ClientOptions.backend = BackendSource.Options(options)`.

<TabItem label="Swift">

```swift
import XmtpSdk

final class AppCredentials: CredentialSource {
    private let load: @Sendable () async throws -> Credential

    init(load: @escaping @Sendable () async throws -> Credential) {
        self.load = load
    }

    func credential() async throws -> Credential {
        try await load()
    }
}

func createAppClient(
    signer: Signer,
    databaseKey: Data,
    loadCredential: @escaping @Sendable () async throws -> Credential
) async throws -> SDKClient {
    let options = ClientOptions(
        backend: .options(options: BackendOptions(
            url: "https://backend.example",
            credentials: AppCredentials(load: loadCredential)
        )),
        storage: StorageOptions(location: .default, encryptionKey: databaseKey)
    )
    return try await SDKClient.create(signer: signer, options: options)
}

func reopenAppClient(
    identity: PublicIdentity, options: ClientOptions, databaseKey: Data
) async throws -> SDKClient {
    var persistent = options
    persistent.storage.encryptionKey = databaseKey
    return try await SDKClient.build(identity: identity, options: persistent)
}

func bearerCredential(token: String, expiresAtSeconds: Int64) -> Credential {
    Credential(name: nil, value: "Bearer \(token)", expiresAtSeconds: expiresAtSeconds)
}
```

Pass the credential source in `BackendOptions.credentials` and pass those options
through `ClientOptions.backend`.

Agent apps pass `backend.credentials` to `Agent.create` or `Agent.createFromEnv`.

Callback failures report a fixed error without the app's error text.

connections use their configured credential source. See [backend auth configuration](/get-started/run-the-backend/#auth).

## Build an existing client

Build, or resume, an existing client (created using [`Client.create()`](#create-a-client)) that's logged in and has an existing local database.

Build requires a database that already holds an identity. It does not register a
new installation and needs no signer. A missing database or an in-memory location
fails with `IdentityNotFound`.

Set `ClientOptions.allowOffline` explicitly for startup without backend requests.
Supplying an `inboxId` alone does not select offline mode on any SDK. Offline
startup needs that ID, or an explicit database path that holds it. A directory
location also needs a saved deployment record for the backend URL. The client
checks stored identity membership. A smart contract wallet check that needs a
network request can fail offline. Offline startup does not disable later network
operations.

## Log out a client

When you log a user out of your app, you can give them the option to delete their local database.

:::tip[Important]
Deleting the local database removes that installation's local message state and keys. A later client needs a new installation unless the app restores a backup. Deletion does not revoke the old installation on the backend.
:::

## Manage database connections

Node, Kotlin, and Swift expose `Storage.reconnect()` through `client.storage`
(JavaScript) or `client.storage()` (Kotlin and Swift). Browser has no reconnect
method. There is no public method to drop a database connection temporarily.
Use `client.end()` when the app releases a client. End a client before replacing
or restoring its storage.

For listener setup, the event catalog, and handlers on each SDK, see [Listen for client events](/sdk/events/).
