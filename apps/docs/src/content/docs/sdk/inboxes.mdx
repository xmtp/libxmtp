With XMTP, a user can have one or more **inboxes** they use to access their messages. An inbox ID is a stable identifier for a user's messaging identity and is used as the destination for messages in direct message and group conversations. It is the SHA-256 digest of the first identity's identifier text followed by a decimal nonce. It does not depend on a key package.

An inbox can have multiple **identities** associated with it. A public identity has an `ethereum` or `passkey` kind and an identifier string. EOA and SCW signers both use an Ethereum identity. A passkey uses a public key encoded as hex.

Messages addressed to these identities use the same inbox ID on the same backend. A new installation must join or sync conversations to obtain their state.

The first time someone uses your app with an identity they've never used with any app built with XMTP, your app creates an inbox ID and **installation** associated with the identity. To do this, you [create a client](/sdk/client/) for their identity.

:::tip[Agent installations]
The installation concepts described in this document apply to both inbox apps and agents. However, the context differs. **Inbox apps** typically have installations across different devices and apps (phone, laptop, different XMTP apps), while **agents** typically have a single installation that is persisted.
:::

The client creates an inbox ID and installation ID associated with the identity. The first identity is the recovery identity. Its signer authorizes identity removal, installation revocation, and recovery identity changes.

![Diagram showing creation of an inbox and installation](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/create-inbox-install.png)

When you make subsequent calls to create a client for the same identity and a local database is not present, the client uses the same inbox ID, but creates a new installation ID.

The backend defaults to 10 active installations per inbox. At the limit, the user needs to [revoke installations](#manage-installations).

![Diagram showing an added installation](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/add-installation.png)

You can enable a user to add multiple identities to their inbox. Adding an identity does not create an installation. A later client created with that identity can register its own installation for the same inbox.

![Diagram showing an added identity](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/add-id.png)

You can enable a user to remove an identity from their inbox. You cannot remove the recovery identity.

## Update and installation limits

### Inbox update limit

The backend defaults to 256 identity log entries per inbox. The operator can change `limits.max_identity_entries`. The creation entry counts. Later entries include actions such as:

- Add a wallet
- Remove a wallet
- Add an installation
- Revoke an installation

:::danger[CRITICAL FOR PRODUCTION]
Inbox updates are cumulative and **cannot be reversed**. Revoking an installation counts as an update but does not decrease the total count. When the log reaches the configured limit, the backend rejects further entries for that inbox.
:::

The backend enforces the limit only when it receives the update. The SDK does not reject it in advance. If the backend rejects an update because the log is full, contact the backend operator. A separate inbox does not inherit the old inbox's conversations.

**Why this limit exists:** Every client that interacts with the inbox must fetch and validate its identity updates. In a group, the work increases for every member with a long update history.

### Installation limit

The backend defaults to 10 active installations per inbox. The operator can change `mls.max_installations_per_inbox`. The SDK reads this limit from server configuration. At the limit, the user must revoke an installation before adding one. The limit controls MLS group size and avoids repeated registration.

:::warning[Important]
The only way to avoid consuming installation updates is to ensure your XMTP database is persisted and reloaded between app sessions and deployments. When you reuse an existing database, you maintain the same installation instead of creating a new one each time.
:::

Installations accumulate per backend. Separate backend deployments have separate identity logs and counts. The same identifier and nonce can derive the same inbox ID in each deployment.

Default and directory storage place the database at `{root}/{deployment}/{inboxId}/xmtp.db3`. A storage label adds a directory below the root. Keep the same storage options to reuse the installation. There is no `env` client option.

### Best practices

1. Reuse the same local database and encryption key on every launch.
2. Point tests at a backend you can reset. Clear its database when a limit blocks the test.
3. Revoke unused installations before the active count reaches the configured limit.
4. Record enough installation data to help a user select the correct device.

### Derive an inbox ID

All four SDKs expose `generateInboxId` to calculate an inbox ID from an identity and nonce. This calculation does not register or move an identity. Client creation uses `registration.nonce` when it needs to derive an inbox ID; the default is `0`. An existing identifier association still selects its current inbox. A new nonce does not reset a full log or merge conversations.

## Manage installations

Show a user the installation ID, last activity time, app version, and device data that your app stores. Revoking an installation removes its authorization from the identity log. It does not delete its local copy of earlier messages.

| Task                           | Browser, Node                                | Kotlin, Swift                                                                                                         |
| ------------------------------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Read inbox state               | `client.inboxState(true)`                    | `client.inboxState(refreshFromNetwork = true)` (Kotlin) or `client.inboxState(refreshFromNetwork: true)` (Swift)      |
| Read several inbox states      | `Client.inboxStates(ids, backend)`           | `SDKClient.inboxStates(ids, backend)` (Kotlin) or `SDKClient.inboxStates(ids: ids, backend: backend)` (Swift)         |
| Revoke selected installations  | `client.revokeInstallations(signer, ids)`    | `client.revokeInstallations(signer, ids)` (Kotlin) or `client.revokeInstallations(signer: signer, ids: ids)` (Swift)  |
| Revoke all other installations | `client.revokeAllOtherInstallations(signer)` | `client.revokeAllOtherInstallations(signer)` (Kotlin) or `client.revokeAllOtherInstallations(signer: signer)` (Swift) |

`InboxState` returns `inboxId`, `identities`, `installations`, `recoveryIdentity`,
and optional `creationSignatureKind`. Static `inboxStates` leaves
`creationSignatureKind` absent. Each installation has `id` and an optional
`createdAt`. The SDK does not return a last activity time or device name. Store
those values in your app if needed.

Static state lookup and revocation need no local client. JavaScript accepts backend
options or a connected `Backend`. Kotlin and Swift use `BackendSource`.

## Add an identity

:::warning
Reassigning an identity that belongs to another inbox moves its identifier lookup to the new inbox. The user loses access through that identity to the former inbox. Enable reassignment only after the user chooses it.
:::

Browser and Node call `client.unsafeAddAccount(signer, allowInboxReassign)`. Kotlin calls `client.unsafeAddAccount(signer, allowInboxReassign)`; Swift calls `client.unsafeAddAccount(signer: signer, allowInboxReassign: allowInboxReassign)`. Use `false` to reject an identity associated with another inbox. Use `true` to permit reassignment. The new identity signs the association; the current installation also signs it.

## Remove an identity

:::tip
You cannot remove the recovery identity.
:::

Use `removeAccount(recoverySigner, identity)` on Browser, Node, or Kotlin. Swift uses `removeAccount(recoverySigner: recoverySigner, identity: identity)`. The recovery signer signs the removal. To remove the current recovery identity, first change the recovery identity with `changeRecoveryIdentifier`.

## Select an identity to display

When an inbox has multiple associated identities, the `identities` array is ordered by the `client_timestamp_ns` field, which sorts identities based on when they were added to the inbox, placing identities with recorded times in ascending order. An identity with no recorded time, including the initial identity, sorts after them. Equal timestamps have no promised order.

For UI display purposes, use the only identity when there is one. Otherwise, use the first non-recovery identity in the ordered array.

## FAQ

### What happens when a user removes an identity?

If the user removes an identity from the inbox, the identity no longer has access to the inbox it was removed from.

![An identity removed from an inbox](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/removed-id.png)

That identity no longer resolves to the former inbox. This does not revoke existing installation keys or erase their local messages. If someone sends a message to the identity, the message is not associated with the original inbox. A later client resolves the identity again. If it has no current association, the SDK falls back to the inbox ID derived from that identity and nonce. Do not assume this always creates a new inbox ID.

### How is the recovery identity used?

The recovery identity and its signer can be used to sign transactions that remove identities and revoke installations. An added identity cannot remove the recovery identity because it does not control the recovery signer.

### Can two inboxes be combined?

There is no way to combine two inboxes. Reassigning an identity from inbox 2 to inbox 1 moves identifier lookup to inbox 1. It does not move the conversations or revoke inbox 2's installations.

![Moving an identity between inboxes](https://raw.githubusercontent.com/xmtp/docs-xmtp-org/refs/heads/main/docs/pages/img/two-inbox-remap-id.png)

To help users avoid this state, ensure that your UX surfaces their ability to add multiple identities to a single inbox.

### Does an associated identity open the existing inbox?

A new client for the identity resolves to the associated inbox. If the identity is reassigned, a new client resolves to the new inbox. Existing installation access is controlled separately through installation revocation.
