---
title: Migrate to a self-hosted backend
description: Update SDK setup, local data, streams, and push notifications when moving from the previous XMTP release.
---

Self-hosted XMTP uses a backend that you run. You must update client setup,
create new local databases, and replace the old push integration. The backend
does not join or copy the previous XMTP network. All participants in a
conversation must use the same deployment.

This guide compares the self-hosted SDKs with
[`main` at `cc878025d`](https://github.com/xmtp/libxmtp/tree/cc878025dab2f93bca18b67fa9fca562a65f2247)
(August 27, 2026). It covers Browser, Node, Agent, Kotlin, Swift, and their
bindings. This is a source baseline, not a shared SDK release number.
React Native is not included in this repository's self-hosted SDKs.

Node and Browser depend on matching `@xmtp/node-bindings` and
`@xmtp/wasm-bindings` versions, respectively: `1.12.0-dev.9f72722`. Let the SDK
install these dependencies; do not replace them with bindings from `main`.

## Migration order

1. [Deploy the backend](/deploy/overview/), then use
   [Run the backend](/get-started/run-the-backend/) for configuration and startup.
2. Select a [published dev release](#published-dev-releases-for-testing) and follow
   the [SDK installation guide](/get-started/install/). An older network SDK
   cannot use this backend.
3. Preserve required history with the old SDK before replacing its database.
   Review the [history limits](#keeping-history) below.
4. Update client options and standalone identity calls. Register users on the
   new backend and create conversations there.
5. Update stream consumers and push handlers. Test with two installations on
   the new backend before moving users.

## Client setup

`backendUrl` is required. There is no default and no fallback. Include the
scheme: `https://` for a public deployment, `http://` for local development.
TLS now follows the URL scheme; remove `isSecure`.

`env` no longer selects a network. It is a string label used in the default
database filename. Android requires one path component, so `../other` is invalid.
Keep the label and database path stable after migration.

| SDK     | Required change                                                                                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser | Pass `{ backendUrl: "https://xmtp.example.com" }` to `Client.create` and `Client.build`. A pre-built WASM `Backend` cannot cross the worker boundary.                                 |
| Node    | Pass `{ backendUrl: "https://xmtp.example.com" }`, or `{ backend }` with a pre-built `Backend`. Do not pass both forms.                                                               |
| Agent   | Set `XMTP_BACKEND_URL` or pass `backendUrl` to `Agent.createFromEnv`. The environment variable takes precedence. Remove `XMTP_GATEWAY_HOST`. `XMTP_ENV` now labels the database only. |
| Kotlin  | Supply `ClientOptions(api = ClientOptions.Api(backendUrl = "https://xmtp.example.com"), ...)`. `env` defaults to `"local"`.                                                           |
| Swift   | Supply `ClientOptions(api: .init(backendUrl: "https://xmtp.example.com"), ...)`. `env` defaults to `"local"`.                                                                         |

See [Create a client](/sdk/client/#create-a-client) for complete examples.
In JavaScript, the default filename label changes from `dev` to `default`.
Swift no longer checks the legacy database filename as a fallback.

### Removed connection and history options

| Previous API                                                                          | Change                                                                                                               |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| JavaScript `apiUrl`; JavaScript and mobile `gatewayHost`                              | Use `backendUrl`. There is one backend endpoint.                                                                     |
| `XmtpEnv`, `ApiUrls`, `HistorySyncUrls`, Node `envToString`; mobile `XMTPEnvironment` | Removed. Use a URL and an optional string database label. Mobile `Client.environment` is now a string.               |
| Mobile `isSecure`                                                                     | Removed. Set the URL scheme.                                                                                         |
| `historySyncUrl`; binding `deviceSyncServerUrl` and `deviceSyncWorkerMode`            | Removed. There is no history-sync server setting.                                                                    |
| `sendSyncRequest`, `sendSyncArchive`, `listAvailableArchives`, `processSyncArchive`   | Removed. Use local archives where applicable. `AvailableArchiveInfo` and mobile `AvailableArchive` are also removed. |
| `VisibilityConfirmationOptions.quorumPercentage` and `quorumAbsolute`                 | Removed. Visibility checks wait for backend readability. `timeoutMs` remains.                                        |

Device preference sync remains available. Removing server-based archive transfer
does not remove `disableDeviceSync`, mobile `deviceSyncEnabled`, or JavaScript
`syncAllDeviceSyncGroups`.

### Standalone identity calls and bindings

JavaScript static `Client.canMessage`, `fetchInboxStates`,
`fetchLatestInboxUpdatesCount`, and `revokeInstallations` now require
`NetworkOptions` or a `Backend`. Node `isAddressAuthorized` and
`isInstallationAuthorized` do too. Replace an omitted argument or an environment
string with explicit connection options.

For direct binding consumers, construct `BackendBuilder` with a backend URL.
Remove `setApiUrl` and `setGatewayHost`; optional `setEnv` sets the database
label. `Backend.backendUrl` replaces `v3Host` and `gatewayHost`; `cacheKey` is
new. Raw client creation no longer takes a separate gateway host. Mobile
`connectToBackend` also takes one backend URL.

### Authentication

Backend authentication is separate from the wallet signer used for XMTP identity.
The backend can require an API key or JWT. See
[authentication configuration](/get-started/run-the-backend/#auth).

All SDKs accept an async `authCallback`: pass it in JavaScript network options
or mobile `ClientOptions.Api`. Agents pass it through their client options.
The callback returns a `Credential` with `value`, `expiresAtSeconds` (Unix
seconds), and optional `name`. The default header is `authorization`. Include
`Bearer` and one space before an API key or JWT.

The middleware caches the credential and requests a new one after expiry or
rejection. Configuration discovery needs no credential and does not invoke the
callback. Callback failures use a fixed error, without app error text.
See [Backend authentication](/sdk/client/#backend-authentication) for examples.
The low-level binding callback and handle APIs remain available.
For direct mobile binding implementations, auth callbacks now throw
`FfiAuthCallbackError.Failed` in Swift or `FfiAuthCallbackException.Failed` in
Kotlin. The dedicated callback error replaces the flat `FfiError`, which could
abort the process when a foreign callback failed.

Swift `getOrCreateInboxId` now returns lookup errors, as Kotlin does. It generates
an ID only after a successful lookup finds none. Handle authentication and
network failures instead of treating them as a new identity.

## New server configuration APIs

The SDK reads the backend's identifier, auth requirements, limits, retention
settings, MLS policy, and supported smart contract wallet chains.

| API                                    | Purpose                                                                                                                                                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Client.fetchServerConfiguration(...)` | Fetch configuration without a client, database, or credential. JavaScript accepts the URL; Swift uses `url:`; Kotlin accepts a URL or `ClientOptions.Api`. Browser also exports `fetchServerConfiguration`. |
| `client.serverConfiguration()`         | Read the snapshot captured when this client was built.                                                                                                                                                      |
| `client.refreshServerConfiguration()`  | Fetch and store configuration for the next build. This does not replace the current client's snapshot.                                                                                                      |

Online client creation fetches configuration when no cached copy exists. It also
fetches when the configured URL changes. Background refresh runs about hourly.
Group size and installation limits now come from the deployment; the defaults
remain 250 group members and 10 installations per inbox.

Handle these new typed errors. JavaScript and Swift use the `Error` suffix;
Kotlin uses `Exception`:

| Error name without suffix  | App action                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| `ConfigurationUnavailable` | Check connectivity and backend compatibility; retry when the cause is resolved.                |
| `ConfigurationInvalid`     | Ask the operator to correct the published configuration.                                       |
| `BackendMismatch`          | Stop using this database for the other deployment. Create a database for the intended backend. |
| `ClientVersionTooOld`      | Upgrade the SDK to meet the backend's minimum libxmtp version.                                 |
| `AuthRequired`             | Configure a credential source supported by the SDK.                                            |
| `ChainNotAccepted`         | Use a supported wallet chain or ask the operator to configure it.                              |

A database is bound to the backend identifier. A URL can change while the
identifier stays the same. A different identifier stops the client and its
streams; a later matching refresh does not clear the stored conflict.
Do not rename a deployment to move it to another server.

## The local database must be recreated

A database created before the transition is rejected with this error:

```text
This database predates the backend transition. Delete the database file and create a new client.
```

The error is not retryable. The SDK leaves the database intact. Export required
history with the old SDK first, and keep a recoverable copy of the database and
its key. Then use a new database path or remove the old database through your
app's migration flow. The new SDK cannot open it to export history.

A new database creates a new installation. Register it on the new backend.
After migration, preserve that database and its encryption key between launches
to avoid creating more installations and reaching the deployment's limit.

On Browser, `Client.close()` is now asynchronous. Await it before database
operations. `Opfs.importDb` requires an absent destination and a current libxmtp
database; it no longer overwrites an existing file. Import changes the database
identity and invalidates earlier delivery cursors and acknowledgement tokens.
It is not a way to convert a pre-transition database.

## Keeping history

There is no server-side transfer of identities, groups, or message history from
the previous network. Plan to create active conversations on the new backend.

:::note[A one-time message import is coming soon]

A one-time import of messages from pre-migration SDKs is in development. It is
not available in the releases above. Until it ships, use the guidance in this
section, and keep a recoverable copy of the old database and its encryption key
so the import can use it later.

:::

Local archive APIs remain: `createArchive`, `archiveMetadata`, and
`importArchive`. Node, Kotlin, and Swift use a file path. Browser uses archive
bytes. See [Backups](/sdk/backups/) for API and encryption-key requirements.

An imported conversation is initially inactive: its local history is readable,
but it has no joined MLS state for sending. On the same backend, an active
member can add the new installation and the conversation can become active.
Restored DMs also remain inactive until the installation joins; a newly created
DM can later be combined with the restored conversation.

:::caution[Archives are not a backend migration]

The archive tests cover installations on the same backend. They do not establish
compatibility between a pre-transition export and this release. An archive
contains local rows, not MLS group keys or backend state. It cannot recreate the
original group on a separate backend. Verify import with your exact old and new
SDK versions before promising history retention, and keep the original backup.

:::

## Message streams and new delivery APIs

Message streams now have tighter guarantees around delivery. Resuming a stream
continues from the position of the last acknowledged message delivered. This is
now true across sessions, network disconnects, and server restarts. A stream can
also start from a particular cursor position.

Because a stream resumes from stored progress, it can deliver retained messages
when it opens, then continue with new messages. Do not assume a stream contains
only messages sent after it starts. Make app side effects safe to repeat.

| Consumer                           | When the SDK acknowledges a message                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| JavaScript or Swift async iterator | When the consumer requests the next item.                                                                     |
| JavaScript `onValue` callback      | After the callback completes successfully. Callback mode starts consumption; do not also iterate that stream. |
| Kotlin `Flow`                      | After the direct collector returns. Adding a buffer changes this boundary.                                    |

Closing or cancelling does not acknowledge the current item. It can be delivered
again. Callback, registered-codec decode, and acknowledgement failures stop
delivery instead of silently dropping the message.

Only one default message reader can own delivery for a database at a time.
Use explicit replay cursors for independent readers.

JavaScript message streams keep the old retry options in their types but ignore
`retry*`, `onFail`, `onRetry`, `onRestart`, and `disableSync`. The core handles
retryable network recovery. This change applies to message streams; do not
assume every conversation or preference stream has the same behavior.

### Streams can replace manual syncing

If your app streams messages, you no longer need to call `conversation.sync()` or
`syncAllConversations` to receive them. The stream does the network catch-up and
records its own progress. For most apps, streams fully replace manual syncing.
Keep an explicit sync only for a specific case, such as a one-time read in a
background handler where no stream runs. See [Sync](/sdk/sync/).

| New API                                                                                                  | Use                                                                                                                                                             |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DecodedMessage.deliveryCursor`                                                                          | Identify a message's position in local delivery. Cursors are opaque and local to a database.                                                                    |
| `messageHistorySnapshot` and `beginningDeliveryCursor` on a conversation or the conversations collection | Read local history with a boundary for subsequent streaming, or start replay from the beginning.                                                                |
| JavaScript stream option `from`; mobile `messageReader` with a `from` argument                           | Replay from a cursor without changing the default consumer's progress.                                                                                          |
| JavaScript `MessageStream` and mobile `MessageReader`                                                    | Observe catch-up with `catchUpSnapshot` and `catchUpChanged`; update scope and filters. JavaScript also exposes `deliveredCursor` and stream option `groupIds`. |
| JavaScript `getStreamFailureDetails(error)`; mobile `error.streamFailureDetails`                         | Read structured catch-up, processing, and publish-confirmation failures.                                                                                        |
| `CatchUpSummary.failed`                                                                                  | Distinguish processing failures from a timeout. Failed processing prevents a successful catch-up result.                                                        |

Network catch-up and app acknowledgement are separate. A publish-confirmation
failure does not prove the write failed. Preserve structured error details when
deciding whether to retry. See [Sync](/sdk/sync/) and [Cursors](/protocol/cursors/).

## Push notifications

The [previous push guide](https://docs.xmtp.org/chat-apps/push-notifs/push-notifs)
uses a separate push server, manual topic subscriptions, and HMAC-key updates.
The self-hosted backend sends notifications itself through APNs, FCM, or HTTPS.

| Previous integration                                                         | Self-hosted integration                                                                                                                           |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Register through `XMTPPush` or push-service stubs                            | Call `client.enableNotifications(config)` on Node, Kotlin, or Swift. Agents use `agent.client`. Browser and WASM do not expose this API.          |
| Maintain `allPushTopics` / `getPushTopics` and resubscribe after key changes | SDK maintains subscriptions, sender-filter keys, and registration renewal while its task runner runs. The old push methods and stubs are removed. |
| Control subscriptions on the separate push server                            | Use `conversation.setNotifications` and `notificationsEnabled`, plus client `notificationState` and `disableNotifications`.                       |
| Process encrypted message bytes from the notification                        | Treat the push as a hint, fetch from the backend, then decrypt locally.                                                                           |

### Operator changes

Configure the backend's [push channels](/deploy/push-configuration/).
APNs needs the operator's key, team ID, key ID, bundle ID, and environment.
FCM needs a Firebase service account. HTTPS delivery can use a host allowlist.
Apps supply their provider token, or an HTTPS receiver URL and a random 32-byte
signing key. Registration fails if the selected channel is not configured.

Retire the old push server and its registrations when the app migration is
complete. The new `disableNotifications` cannot remove old-server registrations.

### App changes

Register again with `enableNotifications`; previous subscriptions and overrides
are not imported. By default, the SDK selects allowed conversations and welcomes,
but excludes device-sync groups, commits, and proposals. Use per-conversation
overrides for mute controls. Enable again when the token or configuration changes.

The new payload contains `topic` and `sequence_id`, with no message bytes:

```json
{
  "topic": "AAECAwQFBgcICQoLDA0ODxA=",
  "sequence_id": "9007199254740993"
}
```

`topic` is base64 of a binary topic. Decode the kind byte and ID; do not pass it
to a legacy string-topic lookup. `sequence_id` is decimal text, not a JavaScript
`number`. APNs delivers a background notification; FCM delivers a data message.
HTTPS also includes `recipient_id` and signed Standard Webhooks headers.

The receiver must open the correct local database, process pending welcomes,
sync the conversation, and read decrypted messages. Apply consent and sender
checks, suppress duplicates, then display a notification. Delivery can be
delayed, repeated, or absent. Continue normal foreground sync. See
[Push notifications](/sdk/push-notifications/) for platform examples, payload
routing, webhook verification, and background-handler responsibilities.

## Other observable changes

- SDK topic strings change from `/xmtp/mls/1/g-<id>/proto` and
  `/xmtp/mls/1/w-<installation-id>/proto` to hex-encoded binary topics:
  `00<group-id>` and `01<installation-id>`. These differ from the base64 push
  field. Update stored routing data and topic parsers.
- Debug API counters now describe `publish`, `query`, `queryNewest`, `subscribe`,
  and `subscribeStatic`. Remove old key-package and group/welcome-specific
  counters. Identity stats remove `publishIdentityUpdate` and
  `getIdentityUpdatesV2`; `verifySmartContractWalletSignature` becomes
  `verifySmartContractWalletSignatures`.
- Node adds `otelServiceName` and `otelSampleRatio` telemetry options. Worker
  configuration adds `WorkerKind.ConfigurationRefresh`.

## Which documentation to use

The public site's
[network environment options](https://docs.xmtp.org/chat-apps/core-messaging/create-a-client),
[history-sync server flow](https://docs.xmtp.org/chat-apps/list-stream-sync/history-sync),
and [app funding flow](https://docs.xmtp.org/fund-agents-apps/get-started) describe
the previous network. Self-hosted deployments use this site's backend setup,
local archives, and SDK push APIs. They do not require an XMTP Gateway Service,
funding an app on the XMTP network, or registration as an xmtpd network node.

Core sending, conversation management, content codecs, and consent APIs retain
their main shapes. Review the changes above before reusing old setup, streaming,
backup, or notification code.
