The new XMTP SDKs use a backend that you operate. The backend does not join or
copy the previous XMTP network. All participants in a conversation must use the
same deployment. Update the app's SDK calls, create new local databases, and
replace the old push integration.

This guide compares two fixed source versions:

| Before                                                                                                  | After                                                                                                          |
| ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| [`main` at `cc878025da`](https://github.com/xmtp/libxmtp/tree/cc878025dab2f93bca18b67fa9fca562a65f2247) | [`self-hosted` at `73447a2431`](https://github.com/xmtp/libxmtp/tree/73447a243195752b2b6c8100082d6e54d8bae27f) |

These are source baselines, not one shared release number. The examples marked
**Before** use the old SDK. The examples marked **After** use the new SDK. Do not
mix imports or generated runtime assets from the two versions. React Native is
not included in this repository's new SDKs.

## Migration order

1. [Deploy the backend](/deploy/overview/) and configure its URL, authentication,
   retention, limits, and optional attachment and push services.
2. [Build and install the matching SDK](/get-started/install/). An older network
   SDK cannot use this backend.
3. Preserve required history with the old SDK. Keep a recoverable copy of each
   database and its encryption key before replacing it.
4. Choose your SDK in [Method-level migration](#method-level-migration). Update
   the signer, client options, method calls, and result handling.
5. Register users and create conversations on the new backend. Test sending,
   reading, restart, stream recovery, and push with two installations before
   moving users.

## Backend, storage, and authentication

Pass an explicit backend URL through `ClientOptions.backend`. Include the
scheme: `https://` for a public deployment, or `http://` for local development.
There is no default network or fallback endpoint. Remove the old `apiUrl`,
`gatewayHost`, and mobile `isSecure` options.

Use `StorageOptions` to select the database location and optional label. A label
names a directory component; it does not select a network. Its default is absent.
The SDK rejects unsafe path components. The Agent SDK retains `XMTP_ENV` as a
storage label and uses `XMTP_BACKEND_URL` for the endpoint.

For a directory location, storage contains an optional label directory, then a
deployment directory and an inbox directory. Keep the database, attachment
directory, and encryption key together. Browser storage does not accept a
database encryption key. Native storage accepts an optional 32-byte key.

Backend authentication is separate from the signer used for XMTP identity.
Supply a credential source, or supply a credential and update it with
`setCredential`. The credential has a header value, an expiry in Unix seconds,
and an optional header name. The default header is `authorization`. For bearer
authentication, include `Bearer` and one space before the API key or JWT.

The SDK caches callback credentials and uses bounded recovery after expiry or
rejection. A direct credential has no refresh callback; the app must replace it.
Configuration discovery does not use credentials or call the credential source.
See [Backend authentication](/sdk/client/#backend-authentication) for each SDK's
credential shape.

### Configuration and errors

`fetchServerConfiguration` takes a backend source and needs no client or database.
Each client keeps the configuration snapshot captured when it was built. Read
`client.serverConfiguration` in JavaScript, or `client.serverConfiguration()` on
mobile. `refreshServerConfiguration()` stores configuration for the next build;
it does not replace the current client's snapshot.

Online creation fetches configuration when no cached copy exists or the URL
changes. Background refresh runs about hourly. The deployment supplies group
and installation limits; the defaults are 250 group members and 10 installations
per inbox.

Handle typed `XmtpError` variants in JavaScript and Swift, or `XmtpException`
variants in Kotlin. The SDK-specific sections show their shapes. Preserve
`ErrorDetails`, including its code, category, retry flag, and any stream failure.

A database is bound to a backend identifier. Its URL can change while the
identifier stays the same. A different identifier records a persistent conflict
and stops backend operations. A later matching refresh does not clear that
conflict. Use a database created for the intended deployment.

## The local database must be recreated

A database created before the transition is rejected with this error:

```text
This database predates the backend transition. Delete the database file and create a new client.
```

The error is not retryable. The SDK leaves the database intact. Export required
history with the old SDK first. Then use a new storage location, or remove the
old database through the app's migration flow. The new SDK cannot open it to
export history and does not provide a conversion API.

A new database creates a new installation. Register it on the new backend.
After migration, preserve the database and its key between launches to avoid
creating more installations and reaching the deployment's limit.

Await client shutdown with `end()` before external database operations. Browser
storage tools are now available through `Storage.admin()`. Import requires an
absent destination and a current database. It does not overwrite an existing
file or convert a pre-transition database. Import changes the database identity
and invalidates earlier delivery cursors and acknowledgement tokens.

## Keeping history

There is no server-side transfer of identities, groups, or history from the old
network. Create active conversations on the new backend.

Local archives use the client's `archives` resource. All SDKs support archive
bytes. Node, Kotlin, and Swift also support archive files. Every archive method,
including metadata reads, requires a separate 32-byte archive key. See
[Backups](/sdk/backups/) for the methods and key handling.

Imported conversations are initially inactive. Their local history is readable,
but they have no joined MLS state for sending. On the same backend, an active
member can add the new installation so that it can join. Restored DMs also remain
inactive until the installation joins; a new DM can later be combined with the
restored conversation.

:::caution[Archives are not a backend migration]
Archive tests cover installations on the same backend. They do not establish
compatibility between a pre-transition export and this source version. An
archive contains local rows, not MLS group keys or backend state. It cannot
recreate the original group on a separate backend. Check import with the exact
old and new SDK versions before promising history retention. Keep the original
backup.
:::

## Streams, sync, and delivery

Message readers can deliver retained messages when they open, then continue
with new messages. Do not assume that a stream contains only new traffic.
Make app effects safe to repeat.

| Consumer                           | Acknowledgement boundary                                                           |
| ---------------------------------- | ---------------------------------------------------------------------------------- |
| JavaScript or Swift async iterator | The next read acknowledges the previous item.                                      |
| JavaScript `onValue` callback      | The stream advances after the awaited callback returns successfully.               |
| Kotlin `Flow`                      | The direct collector returns before the next read. A buffer changes this boundary. |

Closing does not acknowledge the last item. A crash before acknowledgement can
cause repeat delivery. Await work that must finish before acknowledgement.
Custom codec decode errors remain on delivered messages with their original
bytes and error details; they do not silently remove the message.

One default message reader owns delivery progress for a database. An explicit
delivery cursor opens an independent reader without advancing that default
progress. A history snapshot provides a boundary between local history and
subsequent delivery. Cursors are local to their database.

Reader selection stays fixed for the reader's lifetime. Open a new reader to
change it. JavaScript's old retry callbacks and `disableSync` options are removed.
The core handles bounded recovery. A terminal error ends the reader; the app can
open a replacement on the same client. Notification streams have no separate
pre-sync. Use an explicit sync when the app needs a current snapshot first.

Message streams perform network catch-up and local processing. Apps that keep a
message stream open do not need repeated manual sync calls to receive messages.
Explicit `sync`, `conversations.syncAll`, and `catchUpToLive` remain useful
for a fixed read or a background handler. A completed catch-up can report rejected
envelopes: its `failed` count and `completed` flag describe separate results.
An incomplete barrier throws an error with the partial summary in its stream
failure details. See [Sync](/sdk/sync/) and [Cursors](/protocol/cursors/).

If a send returns `PublishedButUnconfirmed`, sync the conversation to finish
confirmation. Do not send the message again.

## Push notifications

Replace the separate push server, manual topic subscriptions, and HMAC-key
updates with the SDK's notification APIs. Node, Kotlin, and Swift expose
`enableNotifications`, `notificationState`, and `disableNotifications`. Agents
use `agent.client`. Browser does not expose these methods.

The SDK maintains subscriptions and registration renewal while its task runner
runs. Use `conversation.setNotifications` for overrides. Read the effective
value from the state snapshot: `group.state().common.notificationsEnabled` or
`dm.state().notificationsEnabled`, with the required `await` or `try` for your
SDK. Re-register after migration; old-server registrations and overrides are
not imported.

Configure the backend's [push channels](/deploy/push-configuration/). APNs needs
the operator's key, team ID, key ID, bundle ID, and environment. FCM needs a
Firebase service account. Apps supply their provider token, or an HTTPS receiver
URL and a random 32-byte signing key. Registration fails if the selected channel
is not configured. Retire the old push server when app migration is complete;
the new `disableNotifications` cannot remove its registrations.

Push payloads contain a base64 binary `topic` and decimal-text `sequence_id`,
with no message bytes. APNs sends a background notification; FCM sends a data
message. HTTPS also includes `recipient_id` and signed Standard Webhooks headers.

Treat a push as a hint. Open the correct database, process pending Welcomes,
sync the conversation, and read decrypted messages. Apply consent and sender
checks and suppress duplicates before showing a notification. Delivery can be
delayed, repeated, or absent. See [Push notifications](/sdk/push-notifications/)
for complete payload routing and handler examples.

The SDK's display topic, such as `[group_message_v1/<hex-id>]`, differs from the
base64 push field. Neither uses the old `/xmtp/mls/1/g-<id>/proto` routing label.
Use the [topic layout](/protocol/topics/) to decode payloads.

### Reopen an OPFS database after migration

The new SDK cannot open a pre-transition database. First create a new database on the target backend with `Client.create`. The examples below compare the reopen APIs; the new example requires a database already created by the new SDK. Old `client.close()` is synchronous. The new shutdown is `await client.end()`. Do not open two clients on one database at the same time.

Old API on main:

```text title="Before (main cc878025da)"
import { Client, type Identifier } from "@xmtp/browser-sdk";

async function reopen(identity: Identifier, oldDbPath: string) {
  const client = await Client.build(identity, { dbPath: oldDbPath });
  client.close();
}
```

Use the new database's actual OPFS entry name for `dbPath` and its attachment directory. Browser paths name OPFS entries; they are not host filesystem paths. The old default was `xmtp-{env}-{inboxId}.db3`. The new default uses the `xmtp-sdk` OPFS pool and a deployment/inbox layout. A default location does not move or convert an old database.

With default or directory storage, offline startup needs the saved backend deployment mapping and the saved inbox ID passed to `build`. Explicit paths do not need that path lookup. `allowOffline: true` permits startup from stored state. It does not prove that the backend used later is compatible.

`Storage.admin()` replaces `Opfs.create()`. It opens an independent lease on the package storage worker. Await `admin.end()` after use. There is no separate `init()` call.

### Send and read messages

The standard send method names remain. All sends use `SendOptions`. The `optimistic` option remains available. `prepareMessage()` stores an unpublished message and queues optimistic publication. It does not keep an app draft private until a later publish call. `idempotencyKey` remains available on the new send options. Compression is optional and uses `"deflate"` or `"gzip"`. If a send fails with `PublishedButUnconfirmed`, call `conversation.sync()` before deciding what to do next. Do not immediately send the content again.

```text title="Before (main cc878025da)"
  await conversation.sendReadReceipt();
  const pending = await conversation.sendText("Send later", {
    optimistic: true,
  });
  await conversation.publishMessages();
  return { id, pending };
}
```

An encrypted-content helper result uses `{ ciphertext, keys }`. The keys record has `secret`, `salt`, `nonce`, `digest`, and `length`. `encryptEncodedContent` accepts serialized envelope bytes. `decryptEncodedContent` returns serialized envelope bytes. These are not the old attachment helper records.

The new attachment API adds `client.attachments` for upload, download, status, and deletion. Browser path sources refer to OPFS. Byte sources copy the caller's bytes at the Browser boundary. Transfer failures preserve a typed attachment cause; the SDK does not add automatic transfer retries.

The new API also adds backend configuration reads, credentials, catch-up state, metadata field descriptors and values, user data, client events, and message actions. These have no direct old Browser method to rename.

### Streams and live events

The signer contract also changes. `SigningKey.publicIdentity`, `.type`, `.chainId`, and `.blockNumber` become suspend `Signer.identity()` and `Signer.kind()`. `sign(message: String): SignedData` becomes `sign(request: SigningRequest): Signature`. Both `Group` and `Dm` provide the methods below. A send returns a hex `MessageId` string. Use `sendText` for text. Use `send(encoded, options)` for a complete envelope or `send(codec, value, options)` for a typed custom value. Standard content does not need registration.

### Codecs, records, and attachments

`Client.register` and the public `CodecRegistry` are removed. The SDK handles the standard catalogue. Pass custom codecs to each `SDKClient.create(..., codecs = listOf(codec))` or `.build(...)`. The registration key uses authority, type ID, and major version. Minor version does not select a separate codec.

`ContentCodec<T>` now requires `T : Any`. Rename `.contentType` to immutable `.type`. Keep `encode`, `decode`, `fallback`, and `shouldPush`; `fallback` and `shouldPush` now have defaults. Return an SDK `EncodedContent(type, parameters, fallback, content: ByteArray)` instead of a protobuf builder. A typed send checks the codec value type. A failed encode, fallback, or push callback fails with `CodecEncodeFailed` before publish.

The standard wrappers include `TextCodec`, `MarkdownCodec`, `AttachmentCodec`, `RemoteAttachmentCodec`, `MultiRemoteAttachmentCodec`, `ReactionV2Codec`, `ReadReceiptCodec`, `ReplyCodec`, `TransactionReferenceCodec`, `WalletSendCallsCodec`, `ActionsCodec`, `IntentCodec`, `GroupUpdatedCodec`, `DeleteMessageCodec`, and `LeaveRequestCodec`. They are optional tools for encode/decode work; they do not need registration. The old JSON `ReactionCodec` is removed. Use `ReactionV2Codec` with `ReactionV2Content(reference, referenceInboxId, reaction)` or `sendReaction` with the new reaction payload.

### Streams, replay, and events

| Old stream                                                                                              | New stream                                                                                                                              |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `group.streamMessages(onClose)` / `dm.streamMessages(onClose)` / `conversation.streamMessages(onClose)` | `conversation.streamMessages(ConversationMessageStreamOptions(from, onClose, onConnectionStateChange))`                                 |
| `conversations.streamAllMessages(type, consentStates, onClose)`                                         | `client.conversations.streamAllMessages(MessageStreamOptions(conversationKind, consentStates, from, onClose, onConnectionStateChange))` |
| `conversations.stream(type, onClose)`                                                                   | `client.conversations.stream(ConversationStreamOptions(conversationKind, consentStates, onClose, onConnectionStateChange))`             |
| `conversations.streamMessageDeletions(onClose)`                                                         | Client events selected with `EventKind.MESSAGE_DELETED`; the event has IDs, not a decoded message                                       |
| `preferences.streamConsent(onClose)`                                                                    | Client events selected with `EventKind.CONSENT_CHANGED`; use the new consent event payload                                              |
| `preferences.streamPreferenceUpdates(onClose)`                                                          | Client events selected with `EventKind.HMAC_KEYS_UPDATED`                                                                               |
| `Client.manageStreamLifecycle`                                                                          | `AndroidStreamLifecycle.enabled`; set it before the first Android client is created                                                     |

The message flows return `Flow<Message>`. Conversation flows return `Flow<Conversation>`. The close callback receives `SDKStreamCloseReason.Closed` or `.Failed(error)`. The connection callback receives the previous nullable `ConnectionState` and the current state.

A default message reader owns persisted delivery progress. Only one can be active in a client database, including across separate group and DM scopes. A second reader fails with `ConsumerOwned`. With direct sequential `collect`, the next read acknowledges the previous message after the collector returns. A buffer can move that boundary before downstream work finishes. Do not use buffered collection as a durable acknowledgement for each consumer.

Use `MessageStreamOptions(from = cursor)` or `ConversationMessageStreamOptions(from = cursor)` for independent replay and live reading. The cursor is exclusive. These readers do not advance default progress. `messageHistorySnapshot(limit: UInt, options)` returns messages and a cursor from one history boundary. `beginningDeliveryCursor()` returns a replay boundary before stored delivery rows. Lower-level `messageReader(...)` / `conversationReader(...)` expose `next()`, `end()`, and connection state methods.

### Implement a signer

`SigningKey` had synchronous identity and kind properties. `Signer` has async throwing methods and requires `AnyObject` and `Sendable`. Sign `SigningRequest.text`. Return a `Signature` enum value rather than `SignedData`.

```swift title="Before"
final class WalletSigner: SigningKey {
    let identity: PublicIdentity
    let signText: (String) async throws -> Data

    init(address: String, signText: @escaping (String) async throws -> Data) {
        identity = PublicIdentity(kind: .ethereum, identifier: address)
        self.signText = signText
    }

    func sign(_ message: String) async throws -> SignedData {
        SignedData(rawData: try await signText(message))
    }
}
```

```swift title="After"
final class WalletSigner: Signer {
    let address: String
    let signText: @Sendable (String) async throws -> Data

    init(address: String, signText: @escaping @Sendable (String) async throws -> Data) {
        self.address = address
        self.signText = signText
    }

    func identity() async throws -> PublicIdentity {
        PublicIdentity(identifier: address, kind: .ethereum)
    }

    func kind() async throws -> SignerKind { .eoa }

    func sign(request: SigningRequest) async throws -> Signature {
        .ecdsa(try await signText(request.text))
    }
}
```

For a smart contract wallet, return `.scw(chainId:blockNumber:)` from `kind()`. Return `.scw(bytes:address:chainId:blockNumber:)` from `sign`. Chain ID and block number are now `UInt64` and `UInt64?`, rather than `Int64?` properties. For a passkey, return `.passkey` from `kind()` and `.passkey(signature:publicKey:authenticatorData:clientDataJson:)` from `sign`. The passkey signature fields are required `Data` values. They are no longer optional fields in `SignedData`.

`PublicIdentity(kind:identifier:)` becomes `PublicIdentity(identifier:kind:)`. `PublicIdentity.identifier` is a stored field in the new Swift record. Do not depend on the old Swift property's lowercase conversion. The core validates and normalizes identities for network operations.

### Send and prepare messages

The old `send(content: Any, options:)` selected a codec from `SendOptions.contentType`. The new API has standard send methods, an encoded-envelope method, and typed codec methods. All sends return `MessageId` (a `String` alias).

```swift title="Before"

    try await dm.send(content: "Hello")
}
```

```swift title="After"
func sendHello(dm: Dm) async throws -> MessageId {
    try await dm.sendText(text: "Hello")
}
```

| ---------------------------------------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |

### Codecs and envelope records

All standard content types are built into the core. An app does not need to register `TextCodec` or other standard codecs to read standard content. Host codecs still support custom types. Pass receive codecs to `SDKClient.create` or `build`. `Client.register(codec:)` and the process-wide registry are absent.

Every codec method changes from a labeled argument to an unlabeled argument: `encode(content:)` becomes `encode(_:)`, `decode(content:)` becomes `decode(_:)`, `fallback(content:)` becomes `fallback(_:)`, and `shouldPush(content:)` becomes `shouldPush(_:)`. Rename the associated type `T` to `Value`, and `contentType` to `type`. `Value` and the codec must be `Sendable`. `Hashable` and `Equatable` are no longer protocol requirements.

```swift title="Before"
struct StatusCodec: ContentCodec {
    typealias T = String
    let contentType = ContentTypeID(authorityID: "example.com", typeID: "status", versionMajor: 1, versionMinor: 0)

    func encode(content: String) throws -> EncodedContent {
        var encoded = EncodedContent()
        encoded.type = contentType
        encoded.content = Data(content.utf8)
        return encoded
    }
    func decode(content: EncodedContent) throws -> String {
        String(decoding: content.content, as: UTF8.self)
    }
    func fallback(content: String) throws -> String? { content }
    func shouldPush(content: String) throws -> Bool { true }
}

func sendStatus(dm: Dm) async throws -> String {
    Client.register(codec: StatusCodec())
    return try await dm.send(content: "Ready", options: SendOptions(contentType: StatusCodec().contentType))
}
```

```swift title="After"
struct StatusCodec: ContentCodec {
    typealias Value = String
    let type = ContentTypeId(authorityId: "example.com", typeId: "status", versionMajor: 1, versionMinor: 0)

    func encode(_ value: String) throws -> EncodedContent {
        EncodedContent(type: type, content: Data(value.utf8))
    }
    func decode(_ encoded: EncodedContent) throws -> String {
        String(decoding: encoded.content, as: UTF8.self)
    }
    func fallback(_ value: String) throws -> String? { value }
    func shouldPush(_ value: String) throws -> Bool { true }
}

func sendStatus(dm: Dm) async throws -> MessageId {
    try await dm.send(StatusCodec(), value: "Ready")
}
```

For receive, create the client with `codecs: [StatusCodec()]`. A typed send applies encode, fallback, and push policy before publishing. An explicit `SendOptions.shouldPush` wins. A standard catalogue type keeps its standard policy. A custom codec's `shouldPush` is used when no explicit value is supplied.

Replace the `ContentTypeText`, `ContentTypeAttachment`, `ContentTypeReply`, `ContentTypeReactionV2`, and other global content constants with `standardContentType(kind:)`. Catalogue kinds include `.text`, `.markdown`, `.reply`, `.reaction`, `.attachment`, `.remoteAttachment`, `.multiRemoteAttachment`, `.readReceipt`, `.transactionReference`, `.walletSendCalls`, `.actions`, `.intent`, `.groupUpdated`, `.deleteMessage`, and `.leaveRequest`.

`EncodedContent` is now a record with `type`, `parameters`, optional `fallback`, and `content`. It is not a SwiftProtobuf message. Replace `serializedData()` / `serializedBytes()` with `encodeEncodedContent(content:)`, and `EncodedContent(serializedBytes:)` with `decodeEncodedContent(bytes:)`. The old `decoded<T>()`, `compress`, and `decompressContent` extension methods are absent. Use a codec or `decodeStandard(encoded:)`; pass compression in send options.

| Content type                       | New record or codec change                                                                                                                                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Text, read receipt                 | `TextCodec.Value` is `String`; `ReadReceiptCodec.Value` is `Void`, rather than `ReadReceipt`. Use `sendReadReceipt()`.                                                                                                                    |
| Markdown                           | `MarkdownCodec` and `sendMarkdown(markdown:)` are explicit.                                                                                                                                                                               |
| Reaction V1                        | `ReactionCodec` is absent. Use `ReactionV2Codec` with `ReactionV2Content`, or `sendReaction`.                                                                                                                                             |
| Reply                              | `ReplyCodec.Value` is `ReplyContent`; encode its body first.                                                                                                                                                                              |
| Attachment                         | `Attachment.data` becomes `content: Data`; `filename` becomes `String?`.                                                                                                                                                                  |
| Remote attachment                  | `scheme` is `String`, rather than `RemoteAttachment.Scheme`; `contentLength` is `UInt32?`, rather than `Int?`. The record initializer is nonthrowing.                                                                                     |
| Multi remote attachment            | `remoteAttachments: [RemoteAttachmentInfo]` becomes `attachments: [RemoteAttachment]`; the nested info type is absent.                                                                                                                    |
| Transaction reference              | Nested `TransactionReference.Metadata` becomes `TransactionMetadata`; fields retain their meanings.                                                                                                                                       |

| Wallet send calls, actions, intent | Use public records `WalletSendCalls`, `WalletCall`, `WalletCallMetadata`, `Actions`, and `Intent`; do not expose `Ffi*` aliases or protobuf records.                                                                                      |

The old `encodeActions`, `encodeAttachment`, `encodeDeleteMessage`, `encodeIntent`, `encodeLeaveRequest`, `encodeMarkdown`, `encodeMultiRemoteAttachment`, `encodeReaction`, `encodeReadReceipt`, `encodeRemoteAttachment`, `encodeReply`, `encodeTransactionReference`, and `encodeWalletSendCalls` functions are absent. The old `decodeActions`, `decodeAttachment`, `decodeDeleteMessage`, `decodeGroupUpdated`, `decodeIntent`, `decodeLeaveRequest`, `decodeMarkdown`, `decodeMultiRemoteAttachment`, `decodeReaction`, `decodeReadReceipt`, `decodeRemoteAttachment`, `decodeReply`, `decodeText`, `decodeTransactionReference`, and `decodeWalletSendCalls` functions are absent. ### Attachments

For an inline attachment, rename the bytes field and use `sendAttachment`.

```swift title="Before"

    try await dm.send(
        content: Attachment(filename: "note.txt", mimeType: "text/plain", data: bytes),

```

```swift title="After"
func sendFile(dm: Dm, bytes: Data) async throws -> MessageId {
    try await dm.sendAttachment(
        attachment: Attachment(filename: "note.txt", mimeType: "text/plain", content: bytes)
    )
}
```

For the deployment's remote attachment service, stage the file first. Send its reference, then upload it. `create(source:)` returns before a network request. `upload()` is a separate async operation.

```swift title="After"
func sendRemoteFile(client: SDKClient, dm: Dm, path: String) async throws -> MessageId {
    let pending = try await client.attachments().create(source: .path(path: path, filename: "note.txt", mimeType: "text/plain"))
    let id = try await dm.sendRemoteAttachment(attachment: pending.remoteAttachment())
    try await pending.upload()
    return id
}
```

`Attachments` adds `offered()`, `create(source:)`, `listPending()`, `pending(remote:)`, `download(remote:)`, `localPath(remote:)`, `listLocal()`, and `deleteLocal(remote:)`. Reads and mutations are async throwing except `offered()`. `PendingAttachment` has `remoteAttachment()`, `localPath()`, `status()`, and `upload()`. `download` returns `DownloadedAttachment(path:mimeType:filename:)`. Download verifies and decrypts the file. A failed download is not retried by that call.

The low-level encryption shape also changes. The old `EncryptedEncodedContent` had flat `secret`, `salt`, `nonce`, `digest`, `payload`, `filename`, and `contentLength` fields. The new record has `ciphertext: Data` and `keys: EncryptionKeys`. Keys contain `secret`, `salt`, `nonce`, `digest`, and `length: UInt64`.

| Old helper                                                                      | New helper                                                                                         | Required change                                                                        |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `RemoteAttachment.encodeEncrypted(content:codec:)`                              | Encode with a codec, serialize with `encodeEncodedContent`, then `encryptEncodedContent(content:)` | Encryption is now async throwing.                                                      |
| `RemoteAttachment.encodeEncryptedBytes(encodedContent:filename:)`               | `encryptEncodedContent(content:)`                                                                  | Filename is separate from encryption output.                                           |

### Streams and replay

Each message or conversation iterator owns a reader. The next read acknowledges the previous message. Cancellation, close, and release do not acknowledge the pending message. Do not advance an app cursor before your app stores or handles the message.

For history followed by live delivery, use the atomic history snapshot and its cursor:

```swift title="After"
        options: ConversationMessageStreamOptions(from: snapshot.cursor)
    )
    for try await message in stream { print(message.id) }
}
```

### Streams, events, and error middleware

`start()` and `stop()` keep their names. `start()` now opens native conversation and message readers without a separate conversation sync. The `start` event reports local reader readiness; the backend can be offline. Conversation events exclude groups already stored locally and include a pending Welcome when it first discovers its group.

`AgentStreamingOptions` and `StreamAllMessagesOptions<T>` now use Node `StreamOptions`: `signal`, `onClose`, and `onConnectionStateChange`. Remove old retry settings, `disableSync`, `onFail`, and `onRestart`. Agent `start()` does not expose a message selection, replay cursor, or `onValue` option.

Core owns network recovery with a finite budget. When a terminal error ends a reader, the Agent closes both readers before it calls error middleware. The old Agent could restart its streams automatically after a handled streaming error. The new Agent requires an explicit `agent.start()` to open a new generation, even when error middleware calls `next()`. A second `start()` while running has no effect. `stop()` ends both readers and permits a later start on the same client.

The event names remain: `actions`, `attachment`, `conversation`, `group-update`, `dm`, `group`, `inline-attachment`, `intent`, `leave-request`, `markdown`, `message`, `multi-attachment`, `reaction`, `read-receipt`, `reply`, `start`, `stop`, `text`, `transaction-reference`, `unhandledError`, `unknownMessage`, and `wallet-send-calls`. Their contexts use the new Node content records. `unknownMessage` now includes unknown content and custom content without a built-in event. The old Agent skipped messages whose decoded content was absent.

Message middleware still runs in registration order. Normal `return` stops the middleware chain and accepts the message without events. `next()` continues to the content event and then `message`. The Agent skips its own inbox. It now waits for async message and conversation listeners. Await all work that must finish before delivery acceptance. A task that runs without `await` does not delay acceptance.

Error middleware still uses `agent.errors.use()`. `next()` handles the error and resumes processing when possible. `next(error)` or a thrown error passes that error to the next handler. Returning without `next()` stops the reader without accepting the failed message. An unhandled message failure has the same effect. A new default reader can deliver the failed message again. Make external actions safe when delivery repeats. Error contexts always have `client`; `message` and `conversation` can be absent.
